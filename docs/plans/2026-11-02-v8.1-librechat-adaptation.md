# v8.1 LibreChat Pattern Adaptation — Implementation Plan

**Base:** `feat/unified-v8-foundation` at `d1b54ae0e520ff0e701e2584f46d523c2348f6f0`  
**Working branches:** `feat/v8.1-advanced-skills` and stacked `feat/v8.1-durable-traces`  
**Pull requests:** [#12 — advanced hash-pinned Skill bundles](https://github.com/soueilouay-creator/uneXpected-/pull/12) and [#15 — durable traces, governed MCP and subagents](https://github.com/soueilouay-creator/uneXpected-/pull/15)

## Goal

Adopt the useful, portable workflow patterns identified in LibreChat while preserving uneXpected as one governed Python runtime, one Coordinator, one PostgreSQL/SQLite state boundary and one command center.

## Architecture decisions

- Extend existing v8 components instead of introducing duplicate coordinators, separate services or another interface.
- Treat external repositories and Skill bundles as untrusted source material until reviewed, pinned and tested.
- Keep connector/tool execution behind registered adapters, capability verification, role permissions and the approval system.
- Preserve existing manifest v1 and API callers while adding optional v2 behavior.
- Do not deploy, enable privileged execution, or retire existing services as part of this branch.

## Adaptation map

| LibreChat pattern | uneXpected adaptation | Current state |
|---|---|---|
| Skills and reusable `SKILL.md` bundles | Extend the current hash-pinned registry with v2 manifest, references, modes, role mapping and metadata-only tool declarations | Implemented on the PR #12 draft branch; CI passed, not merged |
| MCP tools and servers | Add an adapter boundary using existing capability provenance/lifecycle records; enforce role scopes, timeouts, output limits and human approval | In-process adapter boundary implemented in PR #15; no remote MCP transport or external server is configured |
| Subagents | Extend existing role handoffs/graph nodes with bounded child runs, isolated task context, depth/cost/deadline ceilings and summarized return values | Implemented in PR #15: up to 3 sequential child runs, max 4 steps each, bounded depth, isolated supplied inputs and persisted parent_task_id; no parallel execution |
| Execution traces | Standardize event schema and task-linked trace reads for provider timings, adapter calls, retries, cost evidence and terminal status | Task-scoped event cursor reads implemented in PR #15 for SQLite and PostgreSQL; visual trace viewer, live streaming and broader payload redaction remain |
| Resumable streams | Build on persistent task/event records with stable event cursors and reconnect semantics; avoid adding Redis for a single-instance deployment | Authenticated cursor-based event reads are implemented; live streaming and UI trace viewer remain deferred |
| RAG and file intelligence | Start with a provenance-preserving document ingestion/index contract; reuse existing state/database only after query and retention tests | Existing reviewed shared knowledge is present; document indexing not implemented |
| Scheduled automation | Add only after durable queue, transactional approvals/replay and restart/recovery are verified | Not implemented; recurring jobs remain disabled until transactional approval/replay, backup and restart recovery are verified |

## Task 1 — Verified Skill bundles

**Files:** `unexpected_runtime/skills.py`, `unexpected_runtime/models.py`, `unexpected_runtime/coordinator.py`, `unexpected_runtime/storage.py`, `unexpected_runtime/postgres_storage.py`, `unexpected_runtime/http_api.py`, `tests/test_skills_v2.py`, `FILE_INVENTORY_SHA256.txt`, `README.md`, `CHANGELOG.md`.

### Required behavior

1. Keep v1 manifests valid, with existing trigger-matched behavior as the default.
2. Support v2 manifest fields: `invocation_mode`, `description`, `allowed_tools`, and resource entries with relative path, kind and SHA-256.
3. Accept only `automatic`, `user_invocable` and `always_apply`; require explicit user selection for `user_invocable`.
4. Enforce package-root path containment, unique paths, file hashes, UTF-8 for text context, resource-count and byte budgets.
5. Inject only the main Skill file and `reference` resources. Never execute scripts or pass script/asset bytes to the model.
6. Treat `allowed_tools` as metadata; it does not grant capability or permission.
7. Persist requested Skill IDs in the task request payload and include them in idempotency and approval action digests.
8. Expose metadata at authenticated `GET /v1/skills`, accept optional `skill_ids` on `POST /v1/invoke`, and include selected IDs on task detail.
9. Reject unknown, duplicate, inactive, role-mismatched and non-user-invocable selections before provider dispatch.

### Limits

- Maximum 4 explicitly requested Skills.
- Maximum 8 Skills applied to one task.
- Maximum 32 bundle resources per Skill.
- Maximum 256 KiB per bundle file.
- Maximum 64 KiB of injected context per Skill.

### Acceptance checks

- v1 manifest regression remains green.
- v2 automatic, always-apply and manual modes select deterministically.
- Manual selection cannot bypass role mapping or invocation mode.
- Hash tampering and path traversal fail closed.
- Script and asset contents are absent from model context and are never executed.
- API catalog is authenticated and metadata-only.
- Task detail preserves selected IDs; idempotency and approval digests differ when selected IDs differ.
- Full regression suite, compile, PostgreSQL migration checks and Docker smoke test pass.

## Task 2 — MCP adapter boundary

**Implemented files:** `unexpected_runtime/mcp_gateway.py`, Coordinator wiring, authenticated `GET /v1/mcp/tools`, capability verifier association, `tests/test_mcp_gateway.py` and capability documentation.

### Interface contract

- Adapter protocol: `describe() -> ToolDescriptor` and `call(tool_id, arguments, context) -> ToolResult`.
- Each descriptor records source/provenance, adapter version, data access, permissions, cost/risk notes and content digest.
- A tool call receives the requesting role, task ID, deadline, cancellation token and verified execution context. It cannot accept a caller-asserted approval boolean.
- The boundary checks enabled capability state, verified adapter identity, role/tool permission, bounded argument size, deadline and bounded result size.
- External output is untrusted evidence, never executable instructions.
- No MCP network connection or package installation is enabled merely by registering metadata.

### Acceptance checks

- Unknown/disabled/unverified tool calls are rejected before adapter invocation.
- Role mismatch, permission denial, deadline, cancellation and oversized outputs fail closed.
- Adapter/source identity and call outcome appear in task-linked audit events.
- Tests use deterministic fake adapters; no live credential or paid external call is needed for CI.

## Task 3 — Isolated specialist child runs

**Implemented files:** `unexpected_runtime/subagents.py`, Coordinator delegation method, authenticated `POST /v1/subagents/run`, TaskRequest parent lineage, SQLite/PostgreSQL task payloads and `tests/test_subagents.py`.

### Interface contract

- Parent run may request at most a configured small number of child runs, with maximum depth, shared deadline and total-step budget.
- Every child has its own task ID, agent memory namespace and trace parent ID; inherited inputs are copied as data, not as trusted system instructions.
- Child permissions are independently evaluated. Parent approval does not automatically grant a child broader permissions.
- Parent receives a bounded result summary and explicit provenance references, not an unbounded dump of intermediate tool calls.
- Cancellation/deadline of the parent is propagated to active children; terminal children cannot be replayed under a different request digest.

### Acceptance checks

- Child contexts remain isolated across different role IDs.
- Cycles, depth overflow, child-count overflow, deadline overrun and permission escalation are rejected.
- Parent/child lineage is persisted in task payloads and returned by task listing/detail APIs; restart-specific recovery coverage remains required.
- Existing sequential handoff and graph tests remain unchanged and green.

## Task 4 — Execution trace and resumable reads

**Implemented files:** SQLite/PostgreSQL task event cursor methods, authenticated task-events API, event cursor tests and PostgreSQL adapter tests. Command-center trace view and live streaming remain outstanding.

### Interface contract

- Trace events use a stable event ID/cursor, task ID, parent task ID when present, stage, event type, timestamp, bounded metadata and source/provenance references.
- Sensitive values, bearer tokens, provider secrets and raw binary payloads are never stored in trace metadata.
- `GET /v1/tasks/{task_id}/events?after=<cursor>` returns ordered bounded pages and a next cursor; reconnect reads persisted events without repeating side effects.
- Provider and adapter timings/costs are recorded only when actually reported by the provider or measured locally; unknown values stay null.
- UI displays task state and trace history from the same single API/database.

### Acceptance checks

- Sequential cursor pages are ordered and gap-free in tests. Concurrent-append stress coverage remains required.
- Reconnect after simulated client disconnect reads prior events and does not re-invoke the task.
- MCP audit events record hashes and bounded metadata, not raw arguments/results. A general event-payload redaction/allowlist pass remains required.
- SQLite and PostgreSQL behaviors agree on ordering and cursor semantics.

## Task 5 — Document intelligence and governed scheduling

These are intentionally later gates. Document retrieval must add source citations and document-version hashes, and must not treat retrieved text as instructions. Scheduling must use durable queue leases, idempotency, transactional approval/replay storage, bounded retries and verified restart recovery before recurring external actions are permitted.

## Verification and release gates

1. Run focused tests for the change and record expected red/green behavior.
2. Run `python -m compileall -q unexpected_runtime`.
3. Run `python -m unittest discover -s tests -v`.
4. Run the full GitHub Actions workflow including PostgreSQL migrations and Docker image smoke tests.
5. Review changed-file diff, source provenance, hash inventory, security boundaries and API compatibility.
6. Keep PRs #12 and #15 as drafts until their checks pass and code review findings are addressed.
7. Merge the stacked PRs into `feat/unified-v8-foundation` only after owner review; do not target the legacy v7 `main`.
8. A separate deployment and runtime acceptance gate is required after merge; no deployment is implied by repository CI.

## Explicitly out of scope

Full LibreChat deployment, MongoDB/Redis/ClickHouse/RAG API sidecars, separate frontend, phone/PWA app, general shell execution, automatic upstream Skill sync, provider-secret changes, MCP server activation, recurring privileged actions, production cutover and old-service retirement.
